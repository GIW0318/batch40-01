# GSB Bugfix Task
## 题面
客服转过来一句话，说客户只点了一次付款，账单里却出现两笔订单。我顺着调用链查下去，问题不只在订单服务，重试这一层几乎每个判断都反着来。创建订单的 POST 在收到 500 后会自动重试，可请求没带幂等键，下游收到了两次创建请求；429 响应里的 Retry-After 被完全忽略，客户端立刻再打，限流窗口一直被撞；退避没有加抖动，所有实例在同一秒重试，下游看到整齐的脉冲；重试预算按接口各算各的，总重试量超过了正常请求的一成；流式上传的请求体第一次就读完了，重试发出去的是空 body；响应已经写了一部分给调用方，超时后又重试，前端收到两段拼在一起的内容；熔断器半开时把所有请求都放过去，刚恢复的下游又被打满；连接池里取到对端已关闭的连接，TLS 握手失败也被当成可重试；调用方给的截止时间没有往下传，重试三次后总耗时超过上游超时；3xx 跳转后重试计数被清零，两个地址互相跳形成死循环；PATCH 被当成幂等方法重试，库存扣了两次；指标把每次尝试都记成一次请求，成功率看着正常，真实失败率被稀释。http_retry_budget.py 的 RetryBudgetPlanner 要按方法和幂等键判断能不能重试，状态码分类要明确，Retry-After 优先于本地退避，退避带抖动，预算按调用方共享而不是按接口各算，请求体只有在可重放时才允许重试，响应提交后绝不重试，半开状态只放少量探测，截止时间逐跳传递，跳转次数单独限制，尝试次数和请求次数分开统计。现在这十五个用例是红的，改完再谈上线。
